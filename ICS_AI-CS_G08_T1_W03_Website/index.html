Explanation and examples

An AI-powered solution is a structured workflow: an ordered chain of steps that turns a defined input into a useful output for one specific task. Designing it means deciding the task, the data the system needs, the AI step that does the transforming (such as classifying, generating or ranking), and the check that confirms the output is fit for purpose. Building it means assembling those steps so each one feeds the next. At Emerging level the AI step is teacher -mediated or simulated with cards, so students focus on the shape of the workflow rather than on operating a live model. Good design is testable: you can run an example through, inspect the output, and trace any error back to the step that caused it. This traceability is what makes a solution improvable rather than a black box.

Source activity

Hands-on activity guide Overview: Pairs design a five-part workflow for a single specific task, then build and run it once using a simulated, accountfree AI step, tracing the output back to its step. Grouping / timing: Pairs for the design and build; whole class for the trace-back debrief. Tool: A 'simulated AI' card deck or a teacher -curated pre-generated output set for the classify step - account-free, no login, no personal data - chosen so students focus on workflow shape rather than operating a live model. Facilitation steps: 1. Read your task card and write the one specific task in a single sentence. 2. Draw the five boxes: task, input, AI process step, output, check. 3. Decide the input - use only non-personal sample data, never real names or faces. 4. Run one sample input through the simulated AI step and write down the output it returns. 5. Check the output against the task and a trusted reference; mark it fit or not fit. 6. If it is not fit, name which box you would change and why, then note it on your sheet. Unplugged fallback: The simulated AI step is already unplugged - a card deck or paper output set - so the whole activity runs with no device. If cards are unavailable, a partner acts as the 'model', returning a fixed labelled response so the workflow can still be built and traced.
